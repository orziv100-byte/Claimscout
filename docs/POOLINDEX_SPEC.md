## 1. מטרת המוצר

PoolIndex הוא מנוע גילוי, אימות וניטור לארנק קריפטו ציבורי.

המשתמש מכניס כתובת ציבורית פעם אחת. מאותו רגע PoolIndex מבין את הארנק, בודק מקורות רלוונטיים באמת, שומר מצב, חוזר ובודק שוב, ומתריע רק כשמשהו משמעותי משתנה.

PoolIndex אינו ארנק, בורסה, שירות שחזור, או מעבד תשלומים.
PoolIndex אינו דורש seed phrase או מפתח פרטי לסריקה, לניטור או לסוכן.

המוצר אינו רק Airdrop Checker. בדיקת airdrop היא שכבה אחת. הליבה היא:

Wallet → Profile → Select adapters → Verify → Save → Monitor → Detect change → Alert

במקביל, למפעיל בלבד ועם אישור אדם:

Learn → Propose new/repaired source → Sandbox → Approve → Deploy

## 2. כלל זהב

לא מציגים כסף בלי הוכחה.

כל ממצא עובר: Potential → Verification → Verified / Uncertain / Rejected.

יתרת חוזה / בריכה שנשארה **אינה** זכאות של ארנק.

ממצא “שלא הוקלד מראש” פירושו: לא הוקלד מראש **לארנק הזה**. המתאם עצמו יכול להיות בקוד. אין חובת מציאה אקראית מהאינטרנט בלי מתאם.

### 3.2 מוכן אצלנו — צריך שיפור, לא בנייה מאפס

אלה חלקים שכבר קיימים ומרגישים כמו המוצר, אבל **לא ממלאים את ההבטחה**.

| רכיב | מה יש | מה חסר |

| Wallet Check | הדבקת כתובת, סריקה, תווית read-only | התוצאה לא שימושית מול מתחרים |

| Hunt / Deep Hunt | צינור חיפוש קטלוג+GitHub+ארכיון | מחפש טקסט ברשת, לא בוחר מתאמים לפי פרופיל ארנק |

| התראות מייל | אירועי Hunt מוגדרים | לא מחוברים לשינוי מצב ארנק (ממצא חדש / פג תוקף / מקור נכשל) |
| רשימת מקורות | מקודדת בקטלוג + 6 מקורות חיפוש חי | אין Source Manager, אין תדירות/כשל/גרסת מתאם |
| תוכניות Free/Pro | 1 ארנק חינם; Pro מתוכנן $20/חודש או $99/שנה ל־5 ארנקים, התראות מייל, Wayback | שמות ממצאים תמיד חינם. אין pay-to-reveal |

כל עוד שורת 3.2 לא מתוקנת, אין טעם לבנות Agent, EXE, או 100 מקורות.

### 3.3 לבנות מאפס

אין היום מימוש אמיתי של אלה. שלד Hunt אינו תחליף.

1. Wallet Profiler — היסטוריה, רשתות, חוזים, פרוטוקולים, טוקנים, פעילות DeFi רלוונטית.
2. מתאמי בדיקה אמיתיים (RPC / חוזה / API רשמי / merkle / מערכת claim רשמית).
3. Source Manager — רשומת מקור עם מזהה, רשת, קטגוריה, שיטת סריקה, תדירות, rate limit, סטטוס, כשל אחרון, גרסת מתאם.
4. מצב ארנק לאורך זמן — מה נסרק, מה נמצא, מה אומת, מה נדחה, מה השתנה.
5. Scheduler לניטור ארנק: סריקה ראשונה כבדה אחת, אחר כך סריקה יומית קלה.
6. ROI — ערך משוער, עמלה משוערת, נטו, ביטחון, סף התראה. תמיד הערכה.
7. Deadline monitor — רק כשיש תאריך אמיתי.
8. גשר Agent/MCP — משימה מוגבלת, פלט מובנה, בלי הידע הסודי, בלי כתיבה ל-production.
9. צינור תיקון מקורות: כשל → אבחון → הצעת תיקון → sandbox → אישור אדם → שחזור.
10. כלי מפעיל: מעקב מתחרים ופידבק ציבורי (לא מסך משתמש).
11. EXE ל-Windows, עדכון אוטומטי, trial/מנוי כספי — רק אחרי שהמנוע הוכח באתר.

לא ב-v1: Points בלי API רשמי, Future eligibility, חיזוי, Solana/Cosmos כמשפחה מלאה, Telegram/פוש, 10,000 ארנקים, WebSocket לכל המשתמשים.

## 5. ארכיטקטורת המנוע

שני מסלולים נפרדים. לא לערבב.

### מסלול משתמש (מהיר, דטרמיניסטי)

כתובת ציבורית
→ פרופיל
→ בחירת מתאמים רלוונטיים
→ בדיקות אמיתיות
→ אימות
→ סינון הונאה
→ ROI אם ניתן
→ שמירת מצב
→ ניטור
→ שינוי
→ התראה

המאגר הידוע (קטלוג + מתאמים) **הוא** שכבת המשתמש. כך עובדים מתחרים שמצליחים לבדוק ארנק. ההבדל של PoolIndex הוא הפרופיל, האימות, הזיכרון והניטור — לא חיפוש עיוור.

### מסלול מפעיל / סוכן (איטי, עם אישור)

גילוי מקור חדש או מקור שנשבר
→ מחקר
→ sandbox
→ אישור אדם
→ כניסה ל-Source Manager
→ רק אז רץ במסלול המשתמש

סוכן לא מקבל את גרף המקורות, לוגיקת הגילוי, חוקי האימות, הניקוד, או נתוני הלמידה.
סוכן לא כותב לקטלוג החי, לא שולח התראות, לא פותח סריקה כבדה, לא נוגע ב-seed/מפתח.

### איפה רץ המנוע

המנוע, המתאמים והידע רצים **בשרת**.
האתר (ואחר כך ה-EXE) הם לקוח.
אין להוריד קוד מתאם להרצה על מחשב המשתמש.

## 6. אילוצים שלא משתנים

- כתובת ציבורית בלבד. אין seed, אין מפתח פרטי, אין חתימה בשם המשתמש.
- מקור אחד לא מפיל את המנוע: timeout → לוג → מעבר למקור הבא. Retry לכל היותר פעם אחת. בלי לולאה.
- עבודה כבדה אחת בכל רגע. סריקה יומית של ארנק היא קלה; סריקה מלאה היא כבדה ומתוסרת.
- לא ממציאים Eligible / Not eligible כשאין דרך לאמת.
- Closed Beta נשארת בהזמנה עד שהמנוע מוכיח ערך. סריקה “חינם” היא בתוך ההזמנה, לא השקה פתוחה.
- מתאמי ארנק חדשים מותרים; מקורות חיפוש חיים חדשים (Reddit/פורומים וכו') לא מתווספים בבטא בלי החלטה נפרדת.
- לא לוגים של מפתחות, סשן, או תוכנית. לא מוחקים חשבונות/גיבויים בתיקון מנוע.

## 7. תוכניות

הערך החינמי: סריקה ראשונה שמראה שהמנוע באמת בדק, כולל Uncertain כשזו האמת.

הערך בתשלום אינו “שלם כדי לבדוק את הארנק”.
הערך הוא: PoolIndex ממשיך לעבוד על הארנקים כשלא מסתכלים.

Premium מתוכנן אחרי בטא, לפי שימוש אמיתי, ויכול לכלול: ניטור רציף, כמה ארנקים, היסטוריה, ROI, deadline, התראות, ולימים יכולות Agent.

אין מעבד תשלומים בשלבי הליבה. מגבלות 1 / 5 ארנקים כבר קיימות בשרת ויישארו עד החלטה אחרת.

## 8. סדר העבודה

כל שלב מסתיים בהוכחה. השלב הבא לא מתחיל בלי אישור.

### שלב 0 — מחקר Open Source (ימים)

לפני כתיבת מנוע חדש:

1. לחפש מימושים קיימים.
2. לבדוק רישיון.
3. ללמוד ארכיטקטורה בלבד.
4. להשוות לדרישות PoolIndex.
5. לבנות מימוש שלנו.

פרויקטי לימוד שצוינו:

- [airdrop-checker-x402](https://github.com/Br0ski777/airdrop-checker-x402) — MIT. ללמוד MCP, API לזכאות, תוצאה מובנית. לא להעתיק את המוצר.
- [Airdrop-Checker](https://github.com/lif3time-secr3t-c0de/Airdrop-Checker) — רישיון לא מסחרי רגיל. **ארכיטקטורה בלבד. בלי קוד.**

MIT/Apache/BSD אפשר לבחון לפי תנאי הרישיון.
קוד עם מגבלת שימוש מסחרי — לימוד בלבד בלי הרשאה.

תוצר השלב: מסמך קצר מה לומדים, מה אסור להעתיק, ומה בונים אצלנו.

### שלב 1 — ליבת מנוע על ~10 מתאמים אמיתיים (שבועות)

בלי עיצוב חדש. בלי EXE. בלי Agent.

כולל:

- Wallet Profiler רזה (רשתות, טוקנים, חוזים שנגעו — לפי RPC/אינדקסר).
- Source Manager מינימלי (רשומת מקור, לא רק שורה בקטלוג).
- כ-10 מתאמי בדיקה אמיתיים (לא חיפוש GitHub).
- אימות: Verified / Uncertain / Rejected.
- שמירת מצב ארנק.
- סריקה חוזרת והשוואה.
- פלט לבדיקה (לוג/JSON/פקודה או מסך Wallet Check הקיים בלי עיצוב מחדש).

הוכחה:

כתובת אמיתית → פרופיל → מתאמים רלוונטיים → ממצא שלא הוקלד לאותו ארנק → אימות → שמירה → סריקה שנייה → זיהוי שינוי.

### שלב 2 — ניטור והתראה (שבועות, אחרי שלב 1)

- Scheduler: סריקה ראשונה כבדה, אחר כך יומית קלה.
- היסטוריה והשוואת מצב.
- התראת מייל על ממצא חדש מאומת, שינוי סטטוס, או deadline קרוב — בלי הצפה.
- מונים אמיתיים במסך: מקורות שנבדקו, רלוונטיים, Potential, Verified, סריקה אחרונה, סריקה הבאה.
- Watch הקיים נשאר ליתרות קטלוג; ניטור ארנק הוא צינור נפרד.

הוכחה: אותו ארנק, יום אחרי, מקבל התראה רק אם משהו באמת השתנה.

### שלב 3 — Intelligence על הסט הקטן (שבועות)

לשפר, לא להחליף:

- סינון הונאות לממצא (חוזה, דומיין, מקור, רמת אמינות).
- ROI כשאפשר לחשב. סף “אל תתריע מתחת לנטו משוער”.
- Deadline monitor לפריטים עם תאריך.
- Source Manager מלא: תדירות, כשל, גרסת מתאם.

רק אחרי שזה יציב — להרחיב 10 → 50 מתאמים. לא לקפוץ ל-100 לפני שיש אימות+ניטור.

### שלב 4 — חיבור למעטפת הקיימת ובטא מדידה

לחבר את המנוע לאתר שכבר בנינו (Wallet Check, חשבון, Admin).
לא מסכים חדשים אלא אם חסר משטח למונים/היסטוריה.

יעד: עד 50 משתמשים מוזמנים.
למדוד: הרשמה → ארנק → סריקה שהצליחה → Potential → Verified → התראה → חזרה לשימוש.

בטא זו לא דורשת EXE, לא 100 מקורות, ולא Agent.

### שלב 5 — Agent / MCP (אחרי שיש משימות אמיתיות)

- API/MCP של PoolIndex.
- משימה מוגבלת, הרשאות, rate limit, פלט מובנה.
- Bring Your Own Agent (Cursor/Claude) בלי חשיפת הידע הסודי.
- ארכיטקטורה שמאפשרת בעתיד Wallet / Scout / Verification / Recovery / Competitor agents — בלי לבנות את כולם עכשיו.

הוכחה: סוכן חיצוני מקבל משימה אחת ומחזיר תוצאה מובנית.

### שלב 6 — מקור שנשבר

כשל אמיתי או מדומה:

Detect → Diagnose → Research → Suggest fix → Sandbox → Human approve → Restore

בלי Approve אין Restore.

### שלב 7 — למידה ככלי מפעיל

מעקב מתחרים ופידבק ציבורי כמחקר פנימי.
הצעות למקורות חדשים נכנסות לתור אישור.
אין שינוי אוטומטי ב-production.

### שלב 8 — EXE ל-Windows (רק אחרי שהאתר מוכיח את אותו מנוע)

Download → Install → Register → Add Wallet → Scan → Monitor

המשתמש לא צריך Cursor, Node, Python או טרמינל.
ה-EXE מדבר עם השרת. טלמטריה מצומצמת: גרסה, הצלחה/כישלון סריקה, זמן ריצה, שגיאות, קריסות, מקורות שנבדקו, מספר ממצאים.
אין seed/מפתח בטלמטריה.

עדכון: הגדרות מקור מהשרת — כן. הורדת קוד להרצה אצל המשתמש — לא.

Trial/מנוי כספי — אחרי בטא, לפי שימוש.

אחר כך התראת דפדפן במחשב.
Telegram ופוש — אחרי בטא.

רק שינוי משמעותי: ממצא מאומת חדש, סטטוס שהשתנה, deadline קרוב, מקור חשוב שנכשל אחרי שהיה תקין. לא כל Uncertain.

## 12. מבחני הצלחה

יש ליבה טכנולוגית רק אם שני אלה עובדים.

1. ארנק אמיתי → פרופיל → מתאמים רלוונטיים → ממצא שלא הוקלד לאותו ארנק → אימות → שמירה → סריקה חוזרת → שינוי → התראה.
2. מקור שנשבר → אבחון סוכן → הצעת תיקון → sandbox → אישור אדם → שחזור.

## 13. מה לא עושים עכשיו

- לא עיצוב ומסכים שלא נדרשים למנוע.
- לא שיווק לפני שהמנוע מוכח.
- לא בנייה מחדש של תשתית שכבר עובדת (הרשמה, admin, resource guard, גיבויים).
- לא בניית טכנולוגיה קיימת לפני מחקר OSS.
- לא EXE לפני שלבים 1–2.
- לא 50/100 מתאמים לפני אימות + שמירה + סריקה חוזרת.
- לא Agent שכותב ל-production.
- לא seed/מפתח לסוכן, לטלמטריה, או ללקוח.
- לא לולאת retry.
- לא פתיחה ציבורית חינם לפני ממצאים מאומתים על ארנקים אמיתיים.

## 14. זמנים גסים (אדם אחד + עזרה, שרת אחד)

| שלב | זמן |
|---|---|
| 0 מחקר OSS | 2–4 ימים |
| 1 ליבת מנוע ~10 מתאמים | 2–4 שבועות |
| 2 ניטור + מייל | 1–2 שבועות |
| 3 intelligence + הרחבה זהירה | 2–4 שבועות |
| 4 חיבור לאתר + בטא מדידה | 1–2 שבועות |
| 5–6 Agent + מקור שנשבר | 3–5 שבועות |
| 7 כלי מפעיל | מתמשך |
| 8 EXE | 3–6 שבועות |

ליבה שמרגישה אמיתית למשתמש באתר: בערך 6–10 שבועות אחרי תחילת שלב 1.
המוצר המלא כולל EXE ו-Agents: חודשים אחרי שהליבה יציבה.
